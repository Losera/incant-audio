# faust-rs diagnostic-coverage report — 2026-10-09

Point-in-time record. Not maintained after today — see COLLABORATION.md §8 ("a document
that records a point in time must carry a date and then stop changing"). Replaces, for an
upstream-facing audience, the framing previously used for PF-076/issue-#26's conformance
half. Produced by `bench/frs_diag_coverage.py` against `~/.local/bin/faust-rs` (the Aug-30
build; see `docs/records/faust-rs-delta-2026-09-23.md` for why that build's exact commit is
unrecoverable and why that doesn't move any number below — all three available binaries
agree bit-for-bit on this corpus).

## Why this document and not another study

An external adversarial review (requested this session — see
`docs/records/efficacy-adversarial-review-2026-10-09.md` for the full writeup) concluded the
previously-published conformance claim ("51/51 accept/reject agreement") is not a
contribution upstream needs: `grame-cncm/faust-rs` is first-party GRAME (Stéphane Letz, the
Faust author, holds 1,905 of its 1,987 commits) and already runs, in-repo, an
impulse-response oracle generated by the real C++ compiler scoring 133/133 across 8 backends
at 2e-6 tolerance, a 6,624-comparison backend matrix, and — most directly — had already run
the exact comparison this project's claim gestures at: `xtask examples-compare --per-symbol`
over the Faust standard library, 1,110 cases, finding **216 faust-rs rejections C++
accepts, 0 the other way** (`porting/journal/2026-08-07.md`).

What upstream's own fixture corpora genuinely lack is an **error-path** corpus: every one of
`tests/corpus` (277 files), `tests/golden` (242), and `tests/impulse-tests` (133/164) is
positive-path. This project's 202-program, CC-BY-4.0, LLM-generated-and-rejected corpus
(`bench/corpora/repair_corpus_20260830.json`) is complementary on exactly that axis. This
report is what it's offered as: a coverage report over a donatable fixture set, not a claim
about faust-rs's correctness or competitiveness.

## 1. The false-reject screen (closes a real gap in the prior claim)

The previously-published "accept/reject agreement" figure (51/51, 15/15 re-derivable) was
computed **only** over programs the C++ compiler rejects — `build_repair_corpus._attach_frs`
runs faust-rs exclusively on failing rows. Verified this session: of 513 corpus records, 306
are C++-accepted, and **0 of them carry an `frs_codes` field** — faust-rs was never run on a
single one. So the claim had zero coverage of false rejects, the failure mode that matters
most for a compiler port (it's exactly what upstream's own 216/1,110 stdlib finding is).

This report closes that gap:

```
distinct C++-accepted programs : 248
faust-rs rejects a C++-accepted program : 0/248
```

**Clean null.** Not evidence faust-rs has no false rejects in general (248 small,
toy-category LLM outputs is a narrow slice next to upstream's own 1,110-case stdlib sweep,
which did find 216) — but it's a real, previously-missing measurement on the corpus this
project actually has, and it's worth recording plainly rather than leaving the claim
one-sided.

## 2. FRS code distribution on real-world rejected input

```
  69  FRS-PARSE-0001
  68  FRS-PROP-0002
  29  FRS-EVAL-0002
  16  FRS-EVAL-0006
   5  FRS-PROP-0003
   2  FRS-EVAL-0099   <- catch-all
   2  FRS-COMP-0004
   1  FRS-EVAL-0004
```

**8 of the ~30 concrete FRS codes fire at all** on 192 real LLM-generated failures, 73%
concentrated in two codes (`FRS-PARSE-0001` syntax/duplicate-symbol, `FRS-PROP-0002`
routing/arity). 22 codes — including the whole `SFIR`/`FIR`/`LEX`/`CODEGEN` families and
most of `COMP`/`PROP`/`EVAL` — never fire on this corpus at all. That's expected (this is a
narrow slice of toy DSP categories, not an attempt at exhaustive coverage) but it's a
concrete, reusable "what this fixture set does and doesn't exercise" statement that didn't
exist before this report.

## 3. Catch-all hits — upstream-actionable by construction

```
filters-03/L3 (39f24ef2) [FRS-EVAL-0099] stack overflow in eval (depth budget 8192)
trivial-02/L0 (e61b668e) [FRS-EVAL-0099] recursive evaluation loop on node 55
```

Both are drafted as upstream issues this session (see the session handoff / plan file) and
re-verified live against current `main` (`2199d069`, 2026-10-06) before drafting:

- The first (`fi.bandpass(q, fc, fc)` with a slider as filter order) still reports a
  stack-overflow depth-budget error on current `main` — the budget has moved 8192→32768
  (`0e32f8b0`) but the diagnosis is unchanged; it should be a constant-ness error, not a
  depth-budget one.
- The second carries a `cause:` note ("unsupported or malformed intermediate form") that
  reads as a different failure mode from its own headline ("recursive evaluation loop") —
  confirmed byte-for-byte reproducible on current `main`.

Both drafted as separate, narrow, crate-prefixed issues — the shape upstream's actual
accepted contributions (`shakfu` #16/#17/#19) take — not filed by this session.

## 4. What this report deliberately does not claim

- Not a competitiveness or correctness claim about faust-rs as a compiler.
- Not a replacement for upstream's own `examples-compare`/impulse-oracle testing — this
  corpus is two orders of magnitude smaller and entirely toy-category.
- Not a re-run of the LLM-repair-loop A/B (PF-076) — that stays a separate, Incant-internal
  finding about small local models, quarantined pending WP3 (METHODOLOGY.md).

## Reproduction

```bash
PLUGINFORGE_FAUST_RS_BIN=/path/to/faust-rs python3 bench/frs_diag_coverage.py
# or, to compare multiple builds:
python3 bench/frs_diag_coverage.py --bin tag=/path/to/tag/faust-rs --bin main=/path/to/main/faust-rs
```

No model calls, no network beyond the C++ `faust` and `faust-rs` binaries already on disk.
~2 minutes on this machine (506 compiler invocations: 248 C++ accept-side + 192 faust-rs
reject-side + 248 faust-rs accept-side, modulo overlap with the corpus's own cached
`frs_codes`).
