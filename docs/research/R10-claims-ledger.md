# R10 — Claims Ledger

**Purpose:** audit every claim PluginForge/Incant Audio might soon say publicly (press
pitches, README edits, academic submissions, Show HN), before it's said. Read-only research;
no code changed. Every verdict below is read from the cited file:line at HEAD
(`cs375-a2-part-b` branch) on 2026-10-14, not inferred from a commit message or a doc's own
summary of itself — the project's own stated rule (`docs/BUGS.md`'s "a row flips to `fixed`
only after someone reads the cited code" and CLAUDE.md's "a control counts only once it has
been seen failing") is applied here to claims, not just bugs.

Errs toward OVERCLAIM/UNVERIFIED over benefit of the doubt, per instruction — this doc's only
value is catching problems before a reader outside the project does.

## Safe to say publicly today

- "PluginForge/Incant Audio generates real-time audio effect plugins from natural-language
  prompts, compiling to Faust DSL, JIT'd via libfaust/LLVM, running as VST3 or Standalone on
  Linux x86-64." (claim #9 — platform claim is accurate and consistent)
- "Generation includes an automatic compiler-error retry loop (up to 3 attempts) with
  classified error feedback." (claim #1 — mechanism verified real)
- "A dedicated signal-level safety stage (`OutputGuard`) checks for NaN/Inf, blocks DC
  offset, and soft-limits output before it reaches the speakers." (claim #2's mechanism half
  — true as a factual description of what exists, said WITHOUT the word "safe" as a blanket
  reliability guarantee)
- "The project maintains a durable, IDed bug registry and has twice published corrections to
  its own prior public claims" (the dd79b0a / e4507d2 self-correction pattern this audit was
  modeled on) — this is a genuinely differentiating, creditable claim about process, and it's
  true.

## Do not say publicly yet

- **"Sounds like what you asked for" / "generates musical results" / any claim about output
  quality** (claim #10) — zero instrument exists for this. This is the single highest-risk
  item in this ledger: an overclaim here is the one most likely to be falsified by the very
  first person who tries the product and plays a chord or listens critically.
- **"Safe" / "won't damage your output" / "production-ready" as unqualified claims** (claims
  #2, #8) — PF-079 is open and shows 25-40pp of compiling patches are not actually
  render-safe; seven other open defects (PF-032/073/074/081/083/084) directly contradict a
  "reliable" framing.
- **"Polyphonic synthesizers"** (claim #5) — confirmed false against the actual engine. Fix
  the README claim before any press pitch, Show HN post, or demo video that lets anyone play
  a chord.
- **Any specific first-try/retry-corrected/render-safe percentage number** (claims #3, #7) —
  real numbers exist but are stale (pre-date two shipped prompt fixes) and under-powered
  (n=1, not the project's own n≥3 bar). Publishing "92% first-try" or similar today would be
  publishing a number the project's own STATUS.md already calls not-yet-trustworthy.
- **"VST3/AU"** (claim #4) — there is no AU target. Fix in STATUS.md before any copy derived
  from it ships externally.
- **Any claim about binary size or LLVM linkage derived from ADR-001** (claim #6) — the
  "~30MB, must link libfaust+LLVM" language is factually wrong for the current build
  (dynamic linking against system `libfaust.so`, no direct LLVM link).
- **"Self-correcting" phrased as "reads/edits its own broken code"** (claim #1's caveat) —
  PF-081 shows the retry loop never sees the failing program; it blindly regenerates from the
  original spec. The mechanism is real; this specific framing of it is not.
